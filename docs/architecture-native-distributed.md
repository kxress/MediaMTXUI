# Native and distributed architecture

## Repository baseline and current system

The checked-out baseline is `v1.4.0-2-g3579604`: two commits after the `v1.4.0` tag. The working tree was clean before this audit. The application is a Go program (`sidecar/cmd/mtxui`) with a React/Vite frontend embedded into the executable (`sidecar/internal/webui`). The product is described as a sidecar because its initial packaging is Docker Compose; the Go process is already a single executable and does not launch MediaMTX.

The main process loads validated environment settings, creates the database and credential key, reconciles a local `mediamtx.yml`, and starts public and internal HTTP listeners. The application package contains account, role, stream, guest-key, audit, history, recording and holding-screen behavior. SQLite state and encrypted credentials live under the data directory. The UI build is bundled into the Go executable; MediaMTX is a separate process/container. The pinned MediaMTX executable shipped in the image is used to validate candidate configuration, not to run the media server.

## Deployment target boundaries

The application should retain one business-logic implementation. Backend adapters provide a selected MediaMTX instance's Control API, health, version/capabilities, live state, and configuration operations. The local adapter uses the current local file writer and HTTP API. The remote adapter uses the documented Control API over TLS/private transport and a paired optional agent for operations the API cannot safely perform (configuration file validation/write/rollback and narrowly scoped host-local data operations). The agent is not a shell and has no arbitrary path or command endpoint.

Each instance model needs a stable identifier, management endpoint, public media endpoints by protocol, capability set, auth transport, configuration revision/state, and independent health/metrics. The first UI may select one active instance; these fields must not be global assumptions in the model.

MediaMTX remains responsible for ingest, packet forwarding, WebRTC media and distribution. Browsers publish and receive media at the instance's public endpoints; the dashboard only provides administrative APIs/pages and, if retained, a separately bounded signaling compatibility path. A dashboard health failure is not a signal that the media process or active streams stopped.

## Phased implementation plan

1. **Audit and design (this document).** Treat the current tree and its tests as the source of truth; preserve the Docker stack as the compatibility fixture.
2. **Native runtime.** Publish standalone amd64/arm64 Linux binaries containing the frontend, configurable paths/listeners/logging, systemd service templates, and secure install/upgrade/uninstall procedures. Establish a native local MediaMTX service arrangement and remove Docker-only defaults from native examples while keeping current Compose defaults.
3. **Backend boundary.** Define interfaces for API/control, configuration, media endpoints, health/capabilities and local-only features. Adapt current local clients first so application behavior and database formats do not change.
4. **Remote control.** Add per-instance settings and a mutually authenticated/encrypted, narrow agent protocol for validated config transactions, rollback and supported local-file operations. Keep direct MediaMTX API access private; add bounded timeouts, health/retry reporting and fail-closed auth behavior.
5. **Distributed media endpoints.** Make WHIP/WHEP/HLS/media URLs and ICE configuration instance-specific; enable secure cross-origin signaling with appropriate browser auth; verify media flows directly between clients and MediaMTX.
6. **Hardening and regression.** Exercise outage, revocation, drift, rollback, multi-stream, filesystem permission and Docker migration paths. Clearly label capabilities that cannot be provided remotely.
7. **Documentation and release.** Publish Docker, native-local and native-remote instructions, migration/upgrade guidance, checksums and reproducible native artifacts.

## Branch progress

Phase 1 is documented above. Native runtime work adds configurable MediaMTX-local and UI-local log/recording paths, private binds for MediaMTX's HTTP listeners, Linux amd64/arm64 native build targets, systemd units and native install/upgrade/uninstall scripts. Docker defaults and Compose workflows remain intact. CI cross-builds the native target and runs its amd64 binary outside a container as an unprivileged user against the bundled MediaMTX binary.

The first distributed slice adds a fixed-scope mTLS agent, a replay-resistant HMAC auth callback, remote config validation and compare-and-swap updates, central configuration history and rollback, API relay allowlisting, remote capability reporting, and direct WebRTC media with HLS fallback disabled. It supports one remote agent per MediaMTXUI process and keeps recordings, log files and holding clips media-host-local. The media server's Control API, metrics and playback listeners must bind to loopback. This is not yet a multi-instance dashboard or an end-to-end two-host integration test; those remain hardening work.

## Security and migration decisions

Remote management must authenticate both directions and encrypt traffic, either with explicitly configured TLS/mTLS or a secured private transport. MediaMTX's API must not be exposed publicly. The application callback must retain current account/ownership/guest-key decisions and fail closed on timeout or invalid responses. Initial remote auth should be callback based; any future locally verifiable credential mode must define short expiry, rotation, revocation propagation, replay resistance and consistency during a control-plane outage before it is enabled.

Configuration changes must validate with the target MediaMTX version before apply, use a revision/hash precondition, persist a history snapshot, apply atomically on the media host, verify the live API, and restore the previous valid revision if verification fails. Unsupported settings/capabilities must be returned explicitly. Existing SQLite migrations, encryption keys, Compose environment defaults and image tags remain unchanged unless an explicit versioned migration is added.

## Verification strategy

Run existing Go, web and end-to-end suites as regression checks. Add native process/service tests using temporary state directories and an unprivileged account. Add agent protocol tests for identity, authorization scope, timeouts, revision conflicts, validation, apply/rollback, revocation and outage behavior. Add a two-host or network-isolated integration test that has no shared filesystem. For media-plane separation, inspect browser/publisher network targets or capture packets and assert RTP/RTCP and HLS payloads do not traverse the dashboard host. Keep the existing Compose install/upgrade workflow as a compatibility gate.

## Known limits at the audit boundary

The current product is not yet a remote manager. The API proxy and live hub assume one fixed endpoint; auth callback defaults to an internal Docker DNS name and plain HTTP; config management is local-file-only; recordings and holding clips depend on shared paths; and MediaMTX log rotation/tailing depends on a local shared file. Current WebRTC signaling/HLS requests are proxied, even though WebRTC media packets are not. These are implementation work items, not safe assumptions to hide behind a configurable hostname.
